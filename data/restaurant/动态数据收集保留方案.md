# 动态数据现状、预设接口和未来供应商

更新日期：2026-07-30

本文只说明已验证能力和未来可执行接法。当前不能获取独立人流、排队或实时营业数据，
因此生产接口必须明确返回不可用，不能用静态标签、搜索热度、评论数、Mock 或模型
推断冒充实时数据。

## 1. 当前结论

| 动态类型 | 当前生产状态 | 已完成验证 | 主 Agent 默认行为 |
|---|---|---|---|
| 步行路线 `route` | 可用但只允许显式调用 | 5 条高德真实路线测试 | 默认 `not_requested` |
| 人流 `crowd` | `unavailable` | 仅合同/Mock 离线测试 | 显示“暂无实时人流数据” |
| 排队 `queue` | `unavailable` | 仅合同/Mock 离线测试 | 显示“请联系餐厅确认” |
| 实时营业 `live_open_status` | `unavailable` | 仅合同/Mock 离线测试 | 不显示“营业中/已打烊”断言 |

第三阶段真实推荐已暂停。动态数据不可用不能用默认 0 分代替，也不能因此把餐厅排到
前面或后面。

## 2. 为什么现在无法收集

### 2.1 人流

高德普通 POI 搜索不提供可作为独立事实使用的店内实时人数、占用率或客流传感器读数。
本项目也没有以下任一数据授权：

- 餐厅入口客流计数器；
- 商场/物业分区客流；
- Wi-Fi、蓝牙或摄像头匿名化计数；
- 餐厅 POS 桌台占用；
- 商户自主上报。

用“搜索排名、评论量、道路拥堵或地图热度”推断单店人流会产生不可验证结论，当前
禁止。

### 2.2 排队

排队是餐厅运营系统的实时状态，通常需要餐厅部署等候名单系统、桌台系统或人工上报。
本项目没有与澳门餐厅或队列平台签约，也没有餐厅 ID 映射、Webhook 授权和覆盖率
基线，因此不能采集真实等待人数或分钟数。

### 2.3 实时营业状态

高德静态 POI 信息和普通营业时间文本不等于“此刻营业”。临时休息、节假日、厨房
停单、包场和商户未更新都会造成偏差。目前没有商户 webhook 或已验证的实时营业
Provider，因此生产接口返回不可用。

### 2.4 合规和质量

客流传感、Wi-Fi/蓝牙、摄像头和 POS 数据可能涉及个人信息、商户经营数据和合同
限制。供应商接入前必须完成授权、保留期限、用途限制、区域覆盖、误差和服务等级
评估，不能先爬取再补授权。

## 3. 统一 Provider 架构

代码位置：

```text
主要脚本/restaurant_pipeline/providers/
├─ contracts.py
├─ registry.py
├─ factory.py
├─ cache.py
├─ amap.py
├─ unavailable.py
└─ mock.py
```

调用流程：

```text
主 Agent 明确请求
  → Dynamic Agent
  → Provider Registry / Factory
  → 具体 Provider
  → TTL Cache
  → 统一 DTO
  → 主 Agent 展示
```

Provider 类型固定为：

- `route`
- `crowd`
- `queue`
- `live_open_status`

新增供应商只实现对应 Provider，不改主 Agent 的业务字段和错误语义。

## 4. 通用请求

供应商适配前的内部请求建议保持：

```json
{
  "provider_type": "queue",
  "restaurant": {
    "restaurant_id": 123,
    "amap_poi_id": "B0...",
    "name": "餐厅名称",
    "longitude": 113.0,
    "latitude": 22.0,
    "coordinate_system": "GCJ-02"
  },
  "requested_at": "2026-07-30T12:00:00+08:00",
  "locale": "zh-MO",
  "party_size": 2,
  "provider_restaurant_id": null,
  "origin": null
}
```

字段规则：

- `restaurant_id/amap_poi_id` 用于本项目识别；
- `provider_restaurant_id` 只能来自已审核的供应商映射；
- `party_size` 只对排队/预约有意义，未知时为 `null`；
- 路线请求的 `origin` 必须说明来源和是否代理；
- 不在日志中保存用户精确位置，除非主团队另行完成隐私设计和授权。

## 5. 通用响应和状态

建议响应：

```json
{
  "provider_type": "queue",
  "provider_name": "unavailable",
  "status": "unavailable",
  "data": null,
  "fetched_at": "2026-07-30T12:00:00+08:00",
  "expires_at": null,
  "is_stale": false,
  "confidence": null,
  "source_reference": null,
  "error": {
    "type": "provider_not_configured",
    "message": "No approved queue provider is configured."
  }
}
```

允许状态：

| 状态 | 含义 | 前端可否推断业务值 |
|---|---|---|
| `not_requested` | 尚未显式调用 | 否 |
| `success` | Provider 成功且响应通过验证 | 只展示 DTO 明确给出的值 |
| `unavailable` | 无供应商、无覆盖或无授权 | 否 |
| `timeout` | 请求超时 | 否 |
| `rate_limited` | 配额/限速 | 否 |
| `error` | 其他结构化错误 | 否 |

不能把 `unavailable` 转成 0 人、0 分钟或关门；不能把 `timeout` 转成上次永久值。

## 6. 各 Provider 数据字段

### 6.1 `route`

成功数据：

```json
{
  "mode": "walking",
  "distance_m": 820,
  "duration_seconds": 720,
  "origin_source": "user_coordinate",
  "origin_is_proxy": false,
  "destination_source": "restaurant_coordinate",
  "coordinate_system": "GCJ-02"
}
```

当前没有用户实时坐标。测试时必须使用：

```json
{
  "origin_source": "attraction_coordinate_test_proxy",
  "origin_is_proxy": true
}
```

代理路线不能称为“从用户当前位置出发”，不能写入静态关系，也不能覆盖
`straight_distance_m`。

### 6.2 `crowd`

未来成功数据最少包含：

```json
{
  "level": "low|medium|high|unknown",
  "occupancy_ratio": null,
  "observed_count": null,
  "capacity": null,
  "observation_window_seconds": 300,
  "measurement_method": "sensor|pos|merchant_report",
  "coverage_scope": "restaurant|mall_zone",
  "observed_at": "ISO-8601"
}
```

商场分区客流不能无说明映射成单店人流。`occupancy_ratio` 只有分子、分母定义明确时
才能提供。

### 6.3 `queue`

未来成功数据最少包含：

```json
{
  "waiting_parties": 4,
  "estimated_wait_minutes": 25,
  "party_size": 2,
  "queue_accepting_new_entries": true,
  "estimate_method": "provider",
  "observed_at": "ISO-8601"
}
```

“可预约时段”不等于“现场排队 0 分钟”；预约库存、等候名单和实际到店队列必须分别
建模。

### 6.4 `live_open_status`

未来成功数据最少包含：

```json
{
  "open_now": true,
  "business_status": "operational",
  "status_basis": "provider_current_hours|merchant_webhook",
  "next_open_at": null,
  "next_close_at": "ISO-8601",
  "observed_at": "ISO-8601"
}
```

`business_status=operational` 只说明地点总体运营状态，不必然表示当前时刻开门。
只有 Provider 明确提供当前时段/商户事件时才填写 `open_now`。

## 7. 缓存和刷新

动态数据通过 `dynamic_provider_cache` 保存规范请求与响应：

- `cache_key`：Provider 名称、类型、餐厅映射、请求参数的稳定哈希；
- `fetched_at`：实际取得时间；
- `expires_at`：过期时间；
- `status/error_type/error_message`：保留失败语义。

建议初始 TTL（供应商合同可覆盖）：

| 类型 | 建议 TTL | 原因 |
|---|---:|---|
| route | 900 秒 | 当前配置已使用；路线变化相对慢 |
| crowd | 60–300 秒 | 客流变化快 |
| queue | 30–120 秒 | 等候时间变化更快 |
| live_open_status | 60–300 秒 | 需要处理临时状态 |

过期数据只能在 DTO 中显式标记 `is_stale=true` 后作为提示，不能冒充实时。是否允许
stale fallback 应按 Provider 类型配置；排队和实时营业默认不建议静默回退。

## 8. 失败降级

Provider 失败时：

1. 不抛出包含 Key、Token 或完整供应商响应的前端错误；
2. 返回统一状态和可公开错误类型；
3. 日志保存 request ID、HTTP 状态和安全摘要；
4. 不改写静态数据库；
5. 不调用 Mock 代替生产；
6. 主 Agent 保留静态餐厅候选，并显示数据暂不可用。

熔断、重试和限速必须由 Provider 配置控制。对 4xx 权限/参数错误不得盲目重试。

## 9. 未来可合作的数据源

以下是可评估方向，不代表已签约、已覆盖澳门或已获生产许可。

### 9.1 餐厅自有系统 / 商户 webhook（优先）

可由餐厅或集团直接提供：

- 桌台占用、等候人数、预计等待；
- 临时休息/停单/包场；
- 营业状态变更；
- 数据生成时间和门店 ID。

优点是最接近事实；前提是逐店映射、授权、SLA、签名 webhook、重放保护和数据保留
协议。

### 9.2 Waitwhile 等候名单平台

[Waitwhile 官方 Webhooks](https://developers.waitwhile.com/reference/webhooks-2)
支持访问创建/更新以及地点状态更新等事件；官方也提供
[创建 Webhook API](https://developers.waitwhile.com/reference/postwebhooks)。

合作前必须确认：

- 澳门目标餐厅实际使用该平台；
- 商户授权读取对应 location；
- `provider_restaurant_id` 与高德 POI 的人工映射；
- webhook 签名、幂等、重放和断线补偿；
- “访问状态”如何换算等待人数/时间，不能自行猜算法。

### 9.3 OpenTable 预约可用性

[OpenTable 官方 API 文档](https://docs.opentable.com/)说明 API 访问需要申请并获批
集成伙伴、先在 Sandbox 验证、生产访问还需要正式协议；Availability API 可按餐厅、
时间和人数查询可预订时段。

该能力只能表示预约库存，**不能直接表示现场排队**。若未来使用，应建为
`reservation_availability` 或预约扩展，而不是把“有可订时段”写成 `queue=0`。

### 9.4 Google Places 当前营业时间

[Google Places 官方 Place 资源](https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places)
提供 `currentOpeningHours`、`openNow`、下一开关门时间和特殊日期信息；字段的 SKU、
请求 FieldMask 和计费应按
[Place Details 官方文档](https://developers.google.com/maps/documentation/places/web-service/place-details)
评估。

接入难点：

- 需要把高德 POI 与 Google Place ID 做可审核映射；
- 当前营业时间是 Provider 维护的时段推导，不等于商户传感器实时确认；
- `businessStatus=OPERATIONAL` 不能直接解释为 `openNow=true`；
- 需遵守 Google 的展示归属、存储和许可条款。

### 9.5 POS / 订单和桌台系统

例如 [Square Orders API 官方文档](https://developer.squareup.com/docs/orders-api/what-it-does)
和订单 Webhook 可提供订单生命周期事件，但是否能代表现场人流取决于门店系统、订单
来源和授权。线上外卖订单不能当作店内客流；必须由供应商或商户提供明确的桌台/占用
指标。

### 9.6 传感器或物业客流

可评估：

- 门店入口双向计数器；
- 商场/酒店物业的分区客流 API；
- 仅输出聚合数的边缘视觉计数；
- 商户 Wi-Fi/蓝牙匿名聚合。

必须先完成隐私影响评估、匿名化、最小粒度、误差测试、设备离线检测和区域到门店的
映射。没有单店覆盖时只能标记 `coverage_scope=mall_zone`。

## 10. 供应商接入验收门

任何新 Provider 上线前必须全部通过：

1. **商业与合规**：书面授权、澳门覆盖、用途、保留期、展示归属和终止处理。
2. **门店映射**：供应商门店 ID ↔ `amap_poi_id` 人工抽查；名称模糊匹配不能自动发布。
3. **字段语义**：每个数字的单位、时间窗口、分母、更新频率和空值含义明确。
4. **认证安全**：Key/Token 只放环境或密钥服务；Webhook 验签和重放保护。
5. **Sandbox**：固定夹具通过 DTO、错误、限速、超时、TTL 和时区测试。
6. **单店真实测试**：一个餐厅、小时间窗，对照商户后台。
7. **小批量验证**：至少覆盖正常、关闭、无队列、长队、临时停业和无数据场景。
8. **质量阈值**：覆盖率、延迟、空值率、错误率和陈旧率达到书面门槛。
9. **降级**：供应商失败时明确 `unavailable`，不调用 Mock，不污染静态库。
10. **审计**：记录 provider、门店映射版本、请求 ID、时间和原始响应引用。
11. **主 Agent 集成测试**：不自动请求；显式请求、取消、超时和权限错误均正确。
12. **发布批准**：测试报告通过后才把 Provider 从 `unavailable` 切换到生产实现。

## 11. 近期可执行的最小方案

在没有供应商前保持现状：

- 静态餐厅候选和标签正常提供；
- 路线默认不请求，用户选择后显式调用；
- 人流、排队、实时营业显示“暂无已验证动态数据”；
- 提供餐厅电话并标明未独立核验，建议用户致电确认；
- 不推进真实排序，保留契约。

一旦有合作机会，优先选择 1–3 家愿意开放队列/营业 webhook 的澳门餐厅做单店
PoC；先验证事实语义和 ID 映射，再扩大覆盖。
