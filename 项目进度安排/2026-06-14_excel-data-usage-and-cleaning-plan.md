## 1. 分析结论

这批 Excel 数据非常适合把当前 demo 从“路线推荐”升级成“可解释的澳门本地生活决策 Agent”。

它不是普通景点表，而是一套适合比赛展示的“分层画像数据”：

- 主景点表：景点是谁、在哪、几点开、要不要门票。
- 适老化表：景点是否适合老人、轮椅、台阶、休息、厕所、暴晒等。
- 交通表：怎么到、坐什么车、下车后怎么走。
- ID/理由表：给 Agent 做“适合谁、为什么适合”的文字理由匹配。

因此，这批数据最适合支撑“约束驱动的规划”，而不是简单做“海量景点搜索”。

当前 demo 的核心价值应该被表达为：

> 用户输入一句自然语言后，Agent 结合人群画像、路线成本、适老化设施、交通可达性和本地商户执行能力，生成一条可解释、可执行、可调整的澳门半日吃喝玩路线。

## 2. 当前 demo 与数据的关系

当前 demo 已有流程：

```text
用户自然语言输入
→ LLM/Mock LLM 拆解关系、人数、目的、硬约束、软偏好
→ Validator 修正人数和枚举字段
→ Enricher 补全低疲劳、餐桌人数、休息点、避让策略
→ 查询景点和商户
→ Mock 地图 API 判断路线距离、时间、步行量
→ 根据用户类型和约束做可解释评分
→ 生成半日路线
→ 用户确认后模拟预约、订位、点单和消息通知
```

这批 Excel 可以增强其中 4 个环节：

1. 景点候选池
   - 从 20 个 mock 景点扩展到 107 个澳门景点。

2. 约束过滤
   - 根据台阶、轮椅、厕所、休息点、暴晒、步行距离过滤不适合的点。

3. 路线可执行性
   - 使用交通表说明如何到达、下车后怎么走、是否有低地板巴士或轻轨便利。

4. 推荐解释
   - 使用适老化理由和设施字段生成“为什么这样安排”的可解释文案。

## 5. 推荐的数据使用方案

### 5.1 主表作为候选池

主表只负责回答：

- 有哪些景点？
- 名称是什么？
- 在哪个区域？
- 开放时间是什么？
- 是否需要门票？

它不直接承担复杂评分。

建议在 demo 中作为基础索引：

```text
attractions[id] = 景点基础信息
```

### 5.2 适老化表作为路线过滤器

适老化表是最核心的数据。

建议作为：

- 亲子/长者/低疲劳模式的过滤条件。
- 路线评分的主要权重来源。
- 风险解释的主要来源。

示例过滤逻辑：

- 如果用户说“带爸妈”“老人”“不要爬楼梯”：
  - 降低 `stairs_count` 高的点。
  - 降低 `steep_slopes` 为高风险的点。
  - 优先选择有室内休息点、厕所便利、步行距离短的点。

- 如果用户说“亲子”“带孩子”：
  - 优先低疲劳、厕所方便、暴晒低、人流压力低或可控的点。

- 如果用户说“别太累”：
  - 使用步行距离、台阶数、暴晒、人流压力作为主要约束。

### 5.3 交通表作为可执行性证明

交通表可以让 demo 从“推荐景点”变成“真的能去”。

推荐用于回答：

- 怎么去？
- 坐什么车？
- 下车后怎么走？
- 有没有低地板巴士或轻轨？
- 下车后是否有斜路、石级、人流或复杂动线？

在 UI 中可以展示为：

```text
交通建议：乘坐 2、3A、5、10A 等巴士到白鸽巢公园站或高园街站，下车后沿大三巴街方向步行。该片区有斜路和石级，长者建议放慢步速或改乘的士到较近入口。
```

### 5.4 ID/理由表作为可解释输出

ID/理由表适合用于生成：

- 推荐理由
- 适合谁
- 为什么适合
- 有什么注意事项

建议在结果页中输出类似：

```text
推荐理由：这个点以室内参观为主，节奏可控，适合长者慢慢看和中途休息；但仍需核实电梯、无障碍厕所和座椅位置。
```

## 6. 数据清洗计划

### 6.1 第一优先级：必须清洗

#### 6.1.1 清除网页抓取残留

需要从长文本字段中删除：

- `跳至主内容`
- `温度：...`
- `湿度：...`
- `影片共赏`
- `无障碍旅游指南`
- `旅游局网站`
- `文字大小`
- `简体中文`
- `搜索 澳门特别行政区政府...`
- `智能行程规划`
- `计划...`
- `官方简介显示：`

重点字段：

- `senior_tips_zh`
- `other_senior_facilities_uncertain`
- `best_access_route_zh`
- `avoid_route_zh`

#### 6.1.2 统一空值表达

当前存在多种空值/未知表达：

- `官方未说明`
- `待核实`
- `-1`
- `NaN`
- 空字符串

建议统一为：

- 布尔类：`true` / `false` / `unknown`
- 数值类：正常数字 / `null`
- 等级类：`low` / `medium` / `high` / `unknown`
- 文本类：空值为 `unknown` 或展示时显示 `待核实`

#### 6.1.3 统一字段命名

Excel 原始字段适合人工阅读，但不适合程序长期维护。

建议内部字段统一为英文 snake_case：

```text
id
name_zh
name_en
region
latitude
longitude
address
opening_hours_text
ticket_info_text
wheelchair_friendly
has_elevator
steep_slopes
stairs_count
rest_areas
accessible_toilet
senior_tips_zh
best_access_route_zh
avoid_route_zh
```

展示层再映射为中文。

#### 6.1.4 补齐经纬度

当前主表经纬度全部缺失，不利于：

- 地图展示
- 距离排序
- 路线可视化
- 真实导航成本估算

建议优先从以下来源补：

1. 原始抓取数据中的 Google Maps 链接。
2. 澳门旅游局页面。
3. 手动为高频 demo 景点补坐标。
4. 后续如需要，再批量地理编码。

第一阶段不必补满 107 个，可以先补 demo 高频点。

### 6.2 第二优先级：建议清洗

#### 6.2.1 门票字段标准化

当前 `ticket_info` 是长文本。

建议拆成：

```text
is_free
adult_price_mop
student_price_mop
senior_price_mop
child_price_mop
free_policy_text
ticket_note
```

这样可以支持：

- “别太贵”
- “带老人是否免费”
- “亲子预算”

#### 6.2.2 开放时间字段标准化

当前 `opening_hours` 是长文本。

建议先保留原文，同时增加：

```text
opening_hours_text
closed_days
is_open_all_day
last_entry_time
```

第一阶段不要做过度复杂的营业时间计算，比赛 demo 中可以先展示原文和风险提示。

#### 6.2.3 交通字段结构化

当前一行可能包含多条线路。

建议逐步拆成：

```text
transport_type
line_names
boarding_points
dropoff_points
low_floor_status
walking_route_text
walking_risk_tags
```

如果后续要做真实路线搜索，再把多条线路拆成多行。

#### 6.2.4 区域分类统一

建议统一成：

- `macau_peninsula` / 澳门半岛
- `taipa` / 氹仔
- `coloane` / 路环
- `cotai` / 路氹
- `unknown` / 其他

## 7. Demo 产品策略

### 7.1 不建议一开始把 107 个点全部开放给推荐

原因：

- 数据虽然全，但噪声还没完全清理。
- 当前 demo 更需要稳定和可解释，而不是追求覆盖量。
- 比赛演示中，少量高质量路线比大量不稳定推荐更有说服力。

建议第一阶段选择 15-30 个高质量点作为“演示候选池”。

### 7.2 优先增强长者/低疲劳路线

这批数据最强的优势是适老化和交通说明。

因此 demo 最适合重点强化：

- 带爸妈
- 带长辈
- 不要爬楼梯
- 走路少一点
- 需要休息点
- 不要暴晒

这会比普通情侣/朋友路线更有差异化。

### 7.3 产品汇报口径

可以这样介绍：

> 我们不是把景点按热度排序，而是把澳门本地生活数据拆成景点、无障碍设施、交通路径和人群画像四层。Agent 会先理解用户是谁，再根据疲劳、台阶、厕所、休息点、交通到达和商户可用性做多目标决策，最后给出一条能解释、能调整、能执行的半日路线。

## 10. 当前结论

这批数据已经足够支撑一个更强的比赛版本。

最重要的不是“把所有字段都接进去”，而是把它们变成 Agent 的决策理由：

- 为什么推荐这个点？
- 为什么避开另一个点？
- 用户带老人时为什么换路线？
- 下车后怎么走才不累？
- 有哪些设施支持这个判断？

如果能围绕这些问题展示，demo 会明显比普通旅游推荐系统更像一个真正的本地生活 Agent。
